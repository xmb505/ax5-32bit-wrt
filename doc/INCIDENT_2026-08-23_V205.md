## 1. ⚠️ 推翻 INCIDENT_V15 中关于 ubinize 参数的错误结论

**原 v15.0 INCIDENT 文档错误地说**：
> `-m 4096 -p 128KiB -s 4096` 是正确的 AX5 UBI 镜像打包参数

**实际正确参数是**：
> **`-m 2048 -p 128KiB -s 2048`** —— 匹配 AX5 NAND 实际硬件参数 (4 KiB page / 2 KiB subpage)

证据：
1. sys2 (mtd19) 当前跑 v20.4 的 `dmesg` 显示：
   ```
   ubi0: min./max. I/O unit sizes: 2048/2048, sub-page size 2048
   ubi0: VID header offset: 2048 (aligned 2048), data offset: 4096
   ```
2. v20.5 用 `-m 4096 -s 4096` 烧 sys1，sys1 UBI attach 时 `error 22 (Invalid argument)` —— U-Boot 读到 EC header 中 min_io=4096/sub-page=4096，但 NAND 实际是 2048，**kernel/NAND driver 直接拒绝**
3. 改回 `-m 2048 -s 2048` 后 sys1 attach 成功

**为什么 INCIDENT_V15 当时写 -m 4096？** —— 当时 QSDK 12 内核可能跑了 NOR 模式或仿真环境，与真机 NAND 行为不一致。**v15.0 ubinize.cfg 中的注释必须修正**。

## 2. 真正砖机根因链 (v20.4)

其他 AI 烧 v20.4 砖机的完整链：

| 顺序 | 错误 | 后果 |
|---|---|---|
| 1 | 用 mtd-utils **2.3.0** 默认参数 (2048/2048) | 默认 `-m 2048 -s 2048`，EC header 写入 min_io=2048 |
| 2 | rootfs `vol_size=19300352` < squashfs 实际 `19152896` 字节 | 数据溢出 UBI volume 边界，UBI init error 22 |
| 3 | overlay 缺 `vol_flags=autoresize` | overlay volume 不能动态扩展，rootfs 满后挂载失败 |

**v20.4 在 sys2 (mtd19) 上能 attach 正常运行是巧合** —— sys2 之前有旧 squashfs (v20.3 era) 数据残留覆盖了 v20.4 损坏的 UBI 头部。但 sys1 (mtd18) 是干净的全新 flash，v20.4 一上就 brick。

## 3. v20.5 正确参数 (✅ 已在实机验证)

### 3.1 ubinize 命令

```bash
# ⚠️ 必须用 -m 2048 -s 2048，不是 4096！
UBINIZE=/home/xmb505/immortalwrt/ax5-32bit/src/staging_dir/host/bin/ubinize  # mtd-utils 2.1.1
$UBINIZE -o ax5-32bit-v20.5-hakuwrt-release.ubi -m 2048 -p 128KiB -s 2048 ubinize-v205.cfg
```

### 3.2 ubinize-v205.cfg (体积 = 24,117,248 字节, 184 PEBs)

```ini
[kernel]
mode=ubi
image=ax5-32bit-v20.3-hakuwrt-kernel-fit.itb
vol_id=0
vol_size=4194304       # 32 PEBs, 4 MB
vol_type=static
vol_name=kernel

[rootfs]
mode=ubi
image=ax5-32bit-v20.4-hakuwrt-rootfs.squashfs   # 19.1 MB
vol_id=1
vol_size=22020096      # 168 PEBs, 21 MB (squashfs 18.7 MB + 2.3 MB headroom)
vol_type=dynamic
vol_name=rootfs

[overlay]
mode=ubi
vol_id=2
vol_size=126976        # 1 PEB, 124 KB
vol_type=dynamic
vol_name=rootfs_data
vol_flags=autoresize   # 关键：挂载时自动扩展占满剩余 PEBs
```

**注意：mtd-utils 2.1.1 限制** —— **只能有一个卷带 `vol_flags=autoresize`**，否则报 `only one volume is allowed to have auto-resize flag`。所以 rootfs 不能同时加 autoresize。

### 3.3 PEB 预算（mtd18 = 288 PEBs）

| 卷 | PEBs | 大小 |
|---|---|---|
| kernel (static) | 32 | 4 MB |
| rootfs (dynamic) | 168 | 21 MB |
| rootfs_data (autoresize) | 1 → 扩展到 ~88 | ~11 MB |
| **UBI 镜像数据** | **184** | **24 MB** |
| **mtd18 总物理** | **288** | **36 MB** |

### 3.5 验证 ubinize 2.1.1 在哪

```bash
/home/xmb505/immortalwrt/ax5-32bit/src/staging_dir/host/bin/ubinize -V
# 输出: ubinize (mtd-utils) 2.1.1
```

⚠️ **不能用系统默认的 mtd-utils 2.3.0**（`/usr/bin/ubinize`），EC header 兼容性差异。必须用 ax5-32bit 编译树里的 2.1.1。

## 4. 实机烧写 + 切分区流程 (验证通过)

```bash
# 在开发机 (假设 AX5 LAN IP = 10.11.12.1, 密码 nekoneko)
cd /home/xmb505/immortalwrt/ax5-32bit/release

# 1. SCP UBI 到路由器
sshpass -p "nekoneko" scp -O -o HostKeyAlgorithms=+ssh-rsa \
    ax5-32bit-v20.5-hakuwrt-release.ubi root@10.11.12.1:/tmp/v20.5.ubi

# 2. 烧 sys1 (mtd18) —— 注意是 mtd18 不是 mtd19！
sshpass -p "nekoneko" ssh -o HostKeyAlgorithms=+ssh-rsa root@10.11.12.1 \
    'ubiformat /dev/mtd18 -f /tmp/v20.5.ubi -y'

# 3. 切 flag —— sys1 是好的 (failed=0)，强制 sys2 失败 → boot sys1
sshpass -p "nekoneko" ssh -o HostKeyAlgorithms=+ssh-rsa root@10.11.12.1 '
    fw_setenv flag_boot_rootfs 0
    fw_setenv flag_try_sys1_failed 0
    fw_setenv flag_try_sys2_failed 1
    sync
    reboot
'

# 4. 等 60-90s 重连
sleep 90
sshpass -p "nekoneko" ssh -o HostKeyAlgorithms=+ssh-rsa root@10.11.12.1 \
    'uname -r; dmesg | grep "attached mtd" | head -2'
# 期望: "attached mtd18 (name "rootfs")"
```

## 6. 教训清单

1. **永远查真机 dmesg 确认 NAND 硬件参数** —— 不要相信 INCIDENT 文档或别人说的话
2. **UBI init error 22 = 参数不符**，常见原因：min_io/sub-page 不匹配、或 vol_size 溢出
3. **v15.0 ubinize.cfg 中的 -m 4096 -s 4096 注释是错的**，必须改回 -m 2048 -s 2048
4. **刷之前先确认 kernel volume 类型** —— v15.0 INCIDENT 中说 kernel=dynamic，但实际 cfg 是 static，可能在不同次测试中切换过
6. **多卷只有一个 autoresize** —— mtd-utils 2.1.1 硬约束，v15.0 cfg 只有 rootfs 单卷所以不触发
