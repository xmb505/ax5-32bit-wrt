## 2. 为什么是 v20.6 → v21.0 而不是 v18/19/20?

`release/` 目录里从 v18.0 到 v20.6 是一连串**迭代过渡版本**,每次都是上一版小修后
重打的镜像(修改 `/etc/passwd` 加 `ddns-go` 用户、修 ubinize 参数、试错 mtd-utils 版本等)。
它们最终汇聚到 **v20.6 = 真正稳定可出货的最新版**:
- INCIDENT_V205 修复了 `-m 2048 -s 2048` + mtd-utils 2.1.1
- v20.6 在 sys2 (mtd19) 实机冷启动跑 ver1.0.20 验证通过

所以 v21.0 跳过 v18-v20 中间版本,直接基于 v20.6 + 新版 haku_wrt 1.1.2 拼装。

## 3. 拼装流程 (30 秒,纯增量更新)

```bash
cd /home/xmb505/immortalwrt/ax5-32bit/release

# 1. 同步 hakuwrt 源码树到 customize 注入层 (用户日常操作)
cp -av ../hakuwrt/files/usr/bin/haku_wrt customize/usr/bin/haku_wrt
cp -av ../hakuwrt/files/etc/morden_web/config.json customize/etc/morden_web/config.json

# 2. 复用 v20.6 squashfs 作为基线
unsquashfs -d squashfs-root ax5-32bit-v20.6-hakuwrt-rootfs.squashfs

# 3. 注入新版 customize/ 内容
cp -a customize/. squashfs-root/
rm -f squashfs-root/README.md

# 4. 重新打包 squashfs (xz, 128K block — NWRT kernel 唯一支持的格式)
mksquashfs squashfs-root ax5-32bit-v21.0-hakuwrt-rootfs.squashfs -comp xz -b 128K -noappend

# 5. 复用 v20.3 kernel FIT (NWRT 5.4.213 Secure Boot 签名, byte-identical)
cp ax5-32bit-v20.3-hakuwrt-kernel-fit.itb ax5-32bit-v21.0-hakuwrt-kernel-fit.itb

# 6. 用 INCIDENT_V205 修复后的参数打包 UBI
#    ⚠️ -m 2048 -p 128KiB -s 2048 + mtd-utils 2.1.1
$STAGING_DIR/host/bin/ubinize -o ax5-32bit-v21.0-hakuwrt-release.ubi \
    -m 2048 -p 128KiB -s 2048 ubinize-v210.cfg
```

或直接用升级后的脚本(参数化 + 正确 ubinize 路径已内置):

```bash
# 直接 ./pack-ubi.sh (默认 v21.0)
./pack-ubi.sh
# 或 ./customize.sh (会自动调 pack-ubi.sh)
./customize.sh
```

## 5. 顺手修复 (脚本版本化 + ubinize 修正)

v21.0 构建过程中顺手修复了 `release/` 里三个一直存在的隐患:

### 5.1 `pack-ubi.sh` —— 修正 INCIDENT_V205 证实的 ubinize 错误

**修复前**(INCIDENT_V15 文档错误):
```sh
ubinize -o "$OUT" -m 4096 -p 128KiB -s 4096 "$CFG"
#                  ^^^^^^           ^^^^^^
#                  错的             错的
```

**修复后**:
```sh
"$UBINIZE" -o "$OUT" -m 2048 -p 128KiB -s 2048 "$CFG"
# ↑ mtd-utils 2.1.1 绝对路径, 替代系统 /usr/sbin/ubinize 2.3.0
# ↑ -m 2048 -s 2048 匹配 AX5 NAND 实际硬件参数
```

### 5.2 `customize.sh` —— 同步修复 + 参数化

升级为接受 `VER` 参数,默认 v21.0:
```sh
VER="${1:-v21.0}"
# ... 内部调 pack-ubi.sh "$VER"
```

### 5.3 `build.sh` —— 智能识别当前/目标分区

**修复前** —— 硬编码烧 mtd19:
```sh
ubiformat /dev/mtd19 -f "$UBI" -y
#            ^^^^
#            假设运行在 sys1,但如果 sys2 在跑就会失败
```

**修复后** —— 自动检测 cmdline 中的 `ubi.mtd=rootfs[_1]`:
```sh
CMDLINE=$(cat /proc/cmdline)
case "$CMDLINE" in
    *ubi.mtd=rootfs*)   CURRENT=1; TARGET=2; TARGET_MTD=/dev/mtd19 ;;
    *ubi.mtd=rootfs_1*) CURRENT=2; TARGET=1; TARGET_MTD=/dev/mtd18 ;;
esac
ubiformat "$TARGET_MTD" -f "$UBI" -y
# 现在无论从 sys1 还是 sys2 跑 build.sh,都正确烧"对侧"
```

## 6. 后续维护提示

1. **下次拼装新版本**(假设用户编译出 haku_wrt 1.1.3):
   ```bash
   cp -av ../hakuwrt/files/usr/bin/haku_wrt customize/usr/bin/haku_wrt
   cp -av ../hakuwrt/files/etc/morden_web/config.json customize/etc/morden_web/config.json
   ./customize.sh v22.0       # 或 v21.1,看你怎么定版本号
   ./build.sh v22.0
   ```

2. **不要改 `pack-ubi.sh` 里的 -m/-s 参数** —— 这是 INCIDENT_V205 用真机
   dmesg 反复验证的硬件参数,改回 -m 4096 -s 4096 会立即砖机。

3. **不要用系统 `/usr/sbin/ubinize`** —— 那是 2.3.0,与 AX5 NAND 兼容性差。
   一律用 `/home/xmb505/immortalwrt/ax5-32bit/src/staging_dir/host/bin/ubinize` (2.1.1)。

4. **dropbear host key 不需要在 squashfs 里 bake** —— v20.6 起 dropbear
   首次启动会自动生成 RSA-2048 key。v17/v18 早期版本的 baked key 修补
   已经被 dropbear 的运行时生成机制覆盖,这是 OpenWrt 19.07 主线默认行为。
