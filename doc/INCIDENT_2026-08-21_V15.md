## 1. 终极避坑与修复链路（三大核心悬案破案）

在 v14.0 到 v15.0 的迭代中，发生了数次卡 `kernel`、卡 `Starting kernel ...` 以及 `Kernel Panic` 的严重事故。经我们此轮全链路对比，彻底厘清并解决了这三个最底层的闭源驱动与 bootloader 锁死悬案。

### 1.1 悬案一：为什么 U-Boot 报 "Volume kernel not found!" 或卡 UBI init error 12
- **根本原因**：
  - **工具链差异**：工作正常的 v13.8 是由宿主机上的 **`mtd-utils 2.1.1`** 的 `ubinize` 编译的。而新版本使用了 `2.3.0` 等更高版本，它们在 UBI Layout Volume 数据结构中产生不同的头部，导致 AX5 U-Boot 的静态 UBI 挂载器无法成功解析 Layout。
  - **总容量超限**：AX5 sys2 物理分区 `mtd19` 仅有 **36 MB**（288 个 PEBs）。旧配置中，将 `rootfs` 分区设为 24MB 且开启 `autoresize`，同时还声明了 20MB 的 `rootfs_data`。这导致 `ubinize` 打包出来的逻辑 PEB 总和（48MB）远远超出了物理上限（36MB）。U-Boot 挂载 UBI 时，直接因为分配不出对应的内存逻辑页，抛出 **`UBI init error 12 (ENOMEM)`** 并直接死锁。
- **解决方案**：
  1. 回退使用 QSDK 12 主机内置的 **`mtd-utils 2.1.1`** 作为 `ubinize` 的主打包工具。
  2. **像素级对齐 v13.8 物理卷大小**：
     - `Volume 0 (kernel)`: 设为 31 PEBs (`vol_size=3936256`)，类型改为 `dynamic`（对齐 `v13.8`）。这样完全对齐了 `v13.8`，让 U-Boot 读取时不多读任何一字节 trailing garbage（尾部 FF 脏数据），避免其破坏 Device Tree（FDT）加载边界导致卡死。
     - `Volume 1 (rootfs)`: 设为 123 PEBs (`vol_size=15618048`)。刚好能将新打包的 14.78MB 纯净 squashfs 包容进去。
     - `Volume 2 (rootfs_data)`: 设为 1 PEB (`vol_size=126976`)，并开启 **`vol_flags=autoresize`**。这样挂载静态只有 155 个 PEBs（远低于 288 的硬性上限）。但在 UBI 刷写后，控制层会自动将其拉伸扩容填满剩余的所有 133 个 PEBs（约 17MB）。
     - 开机后，内核的 `mount_root` 看到这个足够大（>17 LEBs）的分区，会在首次启动时自动将其格式化为 UBIFS 并挂载为持久化的 `/overlay`。**开箱即用，改配置断电不丢失，和出厂固件完全一致！**

### 1.2 悬案二：为什么好不容易通过 U-Boot 后，启动 27-38 秒发生 NULL pointer dereference Kernel Panic？
- **崩溃特征**：
  ```
  Unable to handle kernel NULL pointer dereference at virtual address 00000000
  PC is at 0x0
  LR is at 0x7f9b0148 [qca_ol@ddc3337b+0x120000]
  CPU: 0 PID: 29 Comm: kworker/0:1 ...
  Workqueue: ipv6_addrconf
  ```
- **根本原因**：
  - 高通私有闭源无线控制脚本 `/lib/wifi/qcawifi.sh` 和 `qwrap.sh` 中包含如下代码：
    `local enable_cfg80211=`uci show qcacfg80211.config.enable | grep "qcacfg80211.config.enable='1'"``
  - 如果 `/etc/config/qcacfg80211` 存在且开启了 `enable '1'`，无线控制层会强制将无线驱动初始化置于 **`cfg80211` 模式**。
  - 然而，高通在 AX5 (IPQ6018) 闭源的 `qca_ol.ko` 驱动模块中，对标准的 `cfg80211` 接口支持极度不全、甚至存在未初始化的回调指针（为 `NULL`）。一旦 `hostapd` 把 AP `ath0` 拉起，内核的 `ipv6_addrconf` 发送接口地址改变通告时，`qca_ol` 触发的回调直接跳转到 `0x0`，从而发生 `bad PC value` 内核崩溃！
  - 黄金母本 `v13.8` 中是**完全没有** `/etc/config/qcacfg80211` 这个文件的，因此默认走的是高通深度测试过的、极度稳定的 **`ioctl/direct` 私有控制模式**。
- **解决方案**：
  - 在打包 squashfs 源码前，**彻底删除 `/etc/config/qcacfg80211` 配置文件**。这会使脚本直接回退到传统 `ioctl` 控制层，彻底根除了 WiFi 初始化导致 Kernel Panic 的致命问题，WiFi 完美启动且不卡不瘫！

### 1.3 悬案三：怎么彻底扬掉 haku_wrt 并实现空密码出厂？
- **根本原因**：
  - 用户明确表示“忘掉 haku_wrt 的事”（即完全不装）。但在先前的 v15.0 rootfs 源码中，依然残留了 7.2MB 的 Go 静态编译后台进程 `haku_wrt` 以及它的 init 启动服务（在 START=99 处抢占 80 端口）。
  - 这版 Go 静态编译 binary 加上 Vue 3 静态资源包极度庞大，且在 AX5 32-bit (arm_cortex-a7) 的早期 musl 环境上运行时容易诱发内存调度冲突。
  - 旧 shadow 中内置的加密哈希是 `'password '`（带空格密码）。很多 SSH 客户端或用户的输入习惯会自动剔除/过滤末尾的空格，导致真实的密码登录验证直接失败。
- **解决方案**：
  1. 完全清理 `/usr/bin/haku_wrt`，`/etc/init.d/haku_wrt` 以及所有 `rc.d` 关联软链接。
  2. 完全清理 `/etc/morden_web` 资源包。
  3. 将 80 端口 and 443 端口完美收回给 `uhttpd`（LuCI Web 服务），实现零冲突。
  4. 将 `/etc/shadow` 中 `root` 账户密码位置**彻底清空**（设为 `root::`），对齐 `v13.8` 原装空密码设置。
  5. 现代 Dropbear v2026.94 对空密码登录提供了原生支持，直接无密码回车便可丝滑秒登，体验极度顺畅！
